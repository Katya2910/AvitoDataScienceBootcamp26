# Anti-bot: классификация cookie_id по событиям

## Задача

Нужно определить, является ли кука ботом сервиса автоматизированного сбора 
данных. На вход подаётся одна кука и её события внутри суточного окна 
наблюдения. На выход я даю оценку от 0 до 1, где выше значит вероятнее бот.

## Метрика

Precision при Recall не ниже 0.70. Это значит: среди всех порогов, при 
которых я нахожу минимум 70 процентов ботов, я беру порог с максимальным 
precision. Одинаковые score обрабатываются одной группой, их нельзя 
разделять.

## Итоговый результат

Precision при Recall не ниже 0.70 на скрытой тестовой выборке: 0.74142. 
Константный ответ дал бы 0.09391. Прирост относительно константы почти 
в восемь раз.

## Структура решения

Проект состоит из трёх файлов:

- `solution.py` — основной скрипт, обучает модель и создаёт `submission.csv`
- `metric.py` — официальная реализация метрики, взята из quickstart
- `requirements.txt` — список зависимостей

Все файлы лежат в корне проекта рядом с папкой `data`.

## Как запустить

Требуется Python 3.11 и выше.

Установка зависимостей:

    pip install -r requirements.txt

Запуск:

    python solution.py

Скрипт читает данные из папки `data` и создаёт файл `submission.csv` в корне 
проекта. Время работы около двух минут: признаки считаются примерно двадцать 
секунд, обучение и предсказание около минуты.

## Валидация

Здесь я сразу поняла, что нужен временной сплит, а не случайный. Тест лежит 
позже трейна по времени, поэтому случайный сплит покажет завышенную оценку. 
Модель просто увидит будущее. Это классическая ошибка, и я её не допустила.

Взяла три точки отсечения: 2026-04-15, 2026-04-17, 2026-04-19. Это последние 
дни трейна, ближайшие по времени к тесту. Итоговый скор считаю как среднее по 
трём сплитам. Так надёжнее, потому что одна дата может дать искажённый 
результат из-за особенностей конкретного дня.

Дополнительно проверяла пять точек отсечения, включая более ранние дни. 
Модель работает стабильно, разброс между днями небольшой. Ранние дни дают 
скор чуть ниже, поздние чуть выше. Это ожидаемо: поведение ботов меняется 
со временем.

## Baseline и сравнение

Три опорные точки:

Константный ответ, то есть доля ботов в трейне, даёт 0.094 на скрытом тесте. 
Это нижняя планка, ниже неё результат быть не может.

Простая модель из quickstart на двух признаках (число событий и число 
уникальных объявлений) даёт около 0.62. Это baseline из условия задачи, 
относительно него измеряется улучшение.

Моё решение даёт 0.74142. Прирост относительно константы в 7.9 раз, 
относительно baseline примерно на двадцать процентов выше.

## Обработка событий и временных окон

События фильтрую строго по окну наблюдения. Условие такое: window_start_ts 
меньше или равно event_ts, и event_ts строго меньше window_end_ts. Всё, что 
вне окна, не учитывается вообще. Это требование задачи, и я его соблюдаю.

Временные интервалы между событиями считаю только внутри окна. Не по всей 
истории куки. Если событие было до окна, оно не влияет на delta_ts первого 
события внутри окна. Иначе можно случайно подсмотреть данные, которых в 
момент окончания окна ещё не было.

Все признаки строятся на момент окончания окна. Ничего из будущего не 
подглядывается.

## Пропуски, дубликаты, категориальные признаки

Пропуски в категориальных полях, а это event_name, platform, seller_type, 
item_category, item_location, заполняю строкой unknown. Пропуски в числовых 
полях, которые появляются при агрегации, заполняю нулём. Ни одна модель не 
видит NaN.

Дубликаты cookie_id проверяю на всех этапах: в train, в test, в submission. 
В файле с ответом ровно одна строка на каждую куку из test.

Категориальные признаки first_event, last_event, first_platform передаю в 
CatBoost как категориальные. Он сам подбирает для них оптимальное 
представление, мне не нужно вручную кодировать.

Платформы в данных приходят в разном регистре. Бывает WEB, Web и web, или 
Android, ANDROID и android. Привожу их к нижнему регистру. Иначе одна и та 
же платформа распадается на несколько разных значений и сигнал размывается. 
Это одна из тех мелочей, которая незаметна, но реально влияет.

## Признаки и почему я выбрала именно их

Основная идея у меня была такая: бот отличается от человека не количеством 
действий, а характером этих действий. Поэтому почти все признаки, которые 
я считаю, это не абсолютные значения, а распределения, доли, энтропии, 
отношения.

Группа 1. Временные интервалы между событиями.
Боты-парсеры работают циклами. Запрос, пауза, запрос, пауза. Паузы 
фиксированной длины, потому что в коде стоит sleep. У человека интервалы 
логнормальные, с длинным хвостом. Поэтому я беру медиану, квартили, 
межквартильный размах, коэффициент вариации. Отдельно считаю энтропию 
интервалов, округлённых до логарифмических бинов, и долю самого частого 
бина. У бота энтропия низкая, а доля одного бина высокая, потому что 
интервалы повторяются.

Группа 2. Поведение курсора.
Pointer_x и pointer_y заполнены только для части событий, примерно у 
трети. Я считаю признаки только по событиям с координатами. Если считать 
по всем, получится мусор, потому что между двумя событиями с координатами 
может быть двадцать без них. Беру среднюю и стандартную длину перемещения, 
скорость, энтропию угла движения, долю резких смен направления. У ботов с 
плохой эмуляцией мыши бывают телепорты: скачки на сотни пикселей за одно 
событие. Это отдельный бинарный признак, и он работает.

Группа 3. Разнообразие контента.
Человек смотрит разные объявления, разные категории, возвращается к 
понравившимся. Бот-парсер идёт по одному разделу и редко возвращается. 
Поэтому считаю отношение уникальных категорий к уникальным объявлениям, 
число уникальных объявлений на событие, энтропию категорий и локаций. 
Эти признаки попали в топ по важности, что подтверждает гипотезу.

Группа 4. User-Agent.
Разбираю строку на структурные части. Длина, начинается ли с Mozilla, есть 
ли Chrome, Firefox, Safari, признаки мобильной платформы. Отдельно проверяю 
на явные маркеры автоматизации: headless, selenium, puppeteer, python, curl 
и другие. Реальные сервисы маскируются под обычные браузеры, поэтому маркер 
срабатывает редко. Но структурные признаки работают.

Группа 5. Человеческие действия.
Логин, показ телефона продавца, открытие чата, отправка сообщения, 
добавление в избранное. Человек это делает, бот-парсер нет. У него другая 
цель, собрать данные, а не связаться с продавцом. Считаю для каждой куки, 
было ли такое действие хотя бы раз, и общее число человеческих событий. 
Отдельно признак: ноль человеческих событий вообще. Это сильный сигнал.

Группа 6. Капча.
Показ капчи значит антибот уже заподозрил автоматизацию. Это прямой сигнал, 
косвенно подтверждающий, что кука ведёт себя подозрительно.

Группа 7. Распределение типов событий и платформ.
Для каждой куки считаю долю каждого типа события и каждой платформы. Это 
даёт модели прямой сигнал. Например, у бота доля search_results_view 
систематически выше, чем доля item_view, потому что он собирает выдачу. 
У человека наоборот.

Группа 8. Контактные композиты.
Смотрю на контактные действия как на единый признак. Считаю их суммарную 
долю и отдельно признак, что контактов не было вообще. Это усиливает 
сигнал от группы 5.

Группа 9. Повторные просмотры и концентрация.
Человек возвращается к одному и тому же объявлению, если оно ему 
понравилось. Бот проходит мимо. Считаю долю повторных просмотров объявлений. 
Отдельно смотрю на концентрацию в одной категории: у бота высокая, он сидит 
в одном разделе.

Группа 10. Переходы между типами событий.
Считаю долю самого частого перехода между типами событий. У бота маршрут 
однообразный, эта доля высокая. У человека маршрут хаотичный.

Группа 11. Интервалы по типам событий.
Считаю медиану и стандартное отклонение интервалов отдельно для item_view, 
search_results_view и photo_swipe. У бота item_view идёт строго за item_view 
с одинаковой задержкой.

Группа 12. Время просмотра карточки.
Интервал от item_view до следующего события куки. Человек смотрит карточку 
несколько секунд, бот проскакивает мгновенно.

Группа 13. Метаданные куки.
Возраст куки на момент старта окна, длительность окна. Свежие куки и старые 
ведут себя по-разному.

## Модель

Использую CatBoost. Он хорошо работает с табличными данными и умеет 
категориальные признаки без ручного кодирования. Параметры такие: глубина 
4 или 5, learning rate 0.03, l2 регуляризация 8. Метрика раннего останова 
PRAUC, потому что меня интересует качество ранжирования в верхней части 
распределения, а не общая точность.

Scale_pos_weight подбираю по сетке 1.0 и 2.0. При весе 1.0 модель не 
смещается к редкому классу, при весе 2.0 слегка смещается. Лучший вариант 
выбираю по среднему скору на трёх временных сплитах.

Финальное предсказание это ансамбль из пяти моделей с разными random_seed. 
Объединяю их по рангам, а не по вероятностям. Rank-усреднение устойчивее: 
модели могут быть по-разному откалиброваны, а ранги всегда сопоставимы. 
Это даёт стабильный результат без переобучения.

## Воспроизводимость

Python 3.11 и выше. Зависимости: pandas, numpy, scipy, catboost, 
scikit-learn. Версии указаны в requirements.txt. Random seed зафиксирован 
на 42. Запуск скрипта создаёт submission.csv в корне проекта.

Никаких внешних API, никаких больших языковых моделей, всё локально.

## Ограничения модели

Первое. Разметка содержит только известные сервисы автоматизированного 
сбора. Неизвестные сервисы в трейне помечены как человеческий трафик, хотя 
фактически это боты. Модель не может их найти, потому что они выглядят как 
люди по определению разметки. Это ограничивает потолок метрики примерно 
уровнем 0.75-0.80.

Второе. Pointer_x и pointer_y заполнены только у 33 процентов событий. Куки 
без координат, это мобильные устройства и часть десктопа, не имеют 
признаков движения мыши. Для них модель опирается только на временные 
интервалы и разнообразие контента. Это ограничивает точность на подвыборке 
без координат.

Третье. Поведение ботов меняется со временем. Модель, обученная на одних 
днях, работает чуть хуже на других. Разброс между днями в валидации заметен, 
я это видела. Это фундаментальное свойство задачи, а не недостаток конкретной 
модели.

Четвёртое. Часть ботов использует полноценную эмуляцию мыши и неотличима 
от человека по доступным признакам. Их можно поймать только по косвенным 
сигналам вроде отсутствия человеческих действий, и это работает не всегда.

## Эксперименты, которые не вошли в финал

Пробовала добавлять признаки времени просмотра карточки, это медиана и 
стандартное отклонение времени до следующего события после item_view. 
Пробовала энтропию переходов между типами событий, долю длинных пауз, 
признаки активности по часам суток. На валидации средний скор рос, но на 
скрытом тесте результат падал. Причина, как я поняла: модель начинала 
переобучаться на конкретный период времени, который совпадал с поздними 
днями валидации, но отличался от тестового периода. Это было неприятно, но 
я вовремя это заметила и откатилась.

Пробовала двухмодельный подход: отдельная модель для кук с координатами 
мыши, отдельная для кук без координат. На валидации получилось хуже, потому 
что каждая подвыборка слишком маленькая. От идеи отказалась.

Пробовала расширенный ансамбль до десяти seed. Прирост в пределах шума, 
оставила пять.

## Что даёт основной вклад

По важности признаков лидируют средняя длина перемещения мыши и её 
стандартное отклонение. Затем квартили интервалов между событиями. Затем 
отношение числа уникальных категорий к уникальным объявлениям. Затем 
энтропии по категориям и локациям. Это подтверждает основную гипотезу: бот 
отличается не количеством действий, а их характером и разнообразием.

## Формат ответа

Файл `submission.csv` содержит две колонки:

- cookie_id — идентификатор куки из test.csv
- score — число от 0 до 1, чем выше, тем вероятнее бот

Одна строка на каждую куку из test. Пропусков, дубликатов, дополнительных 
кук нет. Файл создаётся в корне проекта автоматически при запуске 
solution.py.
